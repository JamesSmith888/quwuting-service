# 匹配与比对细则（matching-playbook）

> 由 SKILL.md 迁出的 Step 2–3 实操细节与历轮踩坑。**红线与当前口径以 SKILL.md 为准**，
> 本文件回答「为什么这么判、踩过什么坑」。

## 1. 城市名归一（🚨 2026-09-10 静默失败事故）

多源的城市名写法不一致：A 源（市井慢时光）用简称「成都/重庆」，B 源（百事通）用「成都市/重庆市」。
两源城市表直接求交时，同一个城市在 `covered` 里变成两个 key（`成都` vs `成都市`）、交集为 ∅
→ **该城被判定为「单源覆盖」→ 两个方向都不自动写库**。

- **表现**：不报错、不异常，只是整城静默不写库（09-10 首跑成都/重庆被整城跳过，漏 3 家暂停）。
- **对策**：`covered` 与 `venue_key` **统一去「市」归一**后再比较；并在写库前打印各城 S 分布自检
  （某批城市 S 集体退化成单元素 = 命中此坑）。
- **修复效果**：09-10 归一后成都补出 3 家暂停（宣乐汇娱乐 #411 / 永恒es舞吧 #456 / 华韵酒吧 #475）。

### 1.1 🚨 header 写法与平台城市**同名但不同城**（2026-09-21 事故）

正文的分区 header 有可能**撞上平台真实城市名**，此时「按 header 猜母城」会整批挂错城，
**同时造成两个方向的错**（假新店 + 假暂停候选）：

- **实证**：某源陕西段 header 序列 = 城中 / 西郊 / 东郊 / **南京** / 北郊 —— 其实写作「**南郊**」的笔误
  （同段门店名单与西安(南)逐条一致，且江苏段根本没有南京名单）。
  而「南京市」是平台真实城市（59 家）⇒ 12 条西安门店被挂到南京市：
  表③ 冒 11 个假新店（缤达/金卡罗/密他/紫夜/喜爱/彼爱/漠河/开运/统领/恋之舞/808）
  **且** 西安市表⑤′ 多出 13 个假暂停候选。
- 🔑 **正解**：**不能只依赖 `cityHeaderMap`** —— 归一优先级必须是「**人工声明的 header_map > 「header+市」词表猜测**」。
  该优先级已固化进 `qw_match.py`（2026-09-21 修正，此前是词表优先，header_map 只能兜底）。
  ⚠️ 若手上是**旧版脚本**或临时手写 matcher：**直接把 mention 的 `city` 改写成不撞词表的写法**
  （例：`西安南郊`）并在 map 里登记，是唯一稳妥的绕法。
- **自检**：比对后扫一眼「有没有哪座城市的 mention 与该城平台门店**几乎全不匹配**」；
  某城 UNMATCHED 突然成堆 = 命中本坑（真新店不会一次冒出十家）。

## 2. Step 2 拉取：稳定排序与翻页漂移

- **export 接口自带 `id ASC`（稳定，首选）**；若降级用公开 `GET /venues`，**必须带 `sort=newest`**
  ——默认 `recommended` 排序无 id tie-break，热度分大多为 0 时排序键重复，翻页边界漂移会
  漏门店（2026-09-01 实测：成都 107 家只返回 81 家、漏 26 家 → 误判 10 家「假新店」）。
- 分页漂移 bug 的完整根因与修复见 `run-history.md § 09-01`。

## 3. 判定优先级与实现约束

比对判定顺序（高 → 低）：**平台别名域 → 数据源字典 → 规则层 → LLM 语义 → UNMATCHED 兜底**。

- 🔑 **平台别名域最优先（2026-09-08 起）**：舞讯名 ∈ 同城候选的 `aliases` → 直接判高置信 EXACT 级；
  别名域里每条都是历次对账确认过的曾用名/错别字/圈内涵称。随之而来的**回写义务**见 §6。
- 🔑 **数据源字典（2026-09-01 起）**：`reference/<数据源>-venue-dict.json`。
  - ⚠️ **DICT_MAP 必须脚本化构建（2026-09-04 教训）**：直接 `json.load` 字典、按 `(city, news_name)`
    自动查映射，**禁止把条目手工抄进比对脚本**（手抄必漏——09-04 漏掉「喜见→芭黎人歌舞厅（喜见）」
    导致误入 UNMATCHED）。舞讯名与 `news_name` 不全等时按「基础名前缀/包含」匹配。
  - **字典命中失败 ≠ 平台没有**：先按条目 `venue_id`（新条目必带）查现状——平台名可能已改带别名
    后缀或整店改名（09-04 蓝迪/蓝波湾两例），查到即用新名更新映射。
  - **推荐实现 = 两段式脚本**：match 脚本（结构化 + 字典映射 + 规则匹配）落盘 JSON，analyze 脚本
    再深挖（反转候选 / CONTAINED 明细 / UNMATCHED 兜底），互不重跑。
    🔧 **已固化**（2026-09-14）：`scripts/qw_match.py` 即 match 段——吃 mentions JSON、自带 export
    拉取、内置别名域/字典/规则/三道兜底，落盘命中 JSON + 摘要；**不要再每轮手写 matcher**。
    配套 `scripts/qw_analyze.py` = analyze 段（反转候选 / 新店候选 / 暂停候选 + 提交前自检）。
  - `removed_duplicates` 段 = 用户确认删除的重复数据，命中即跳过；但**先查正本**（见 §5）。
  - `uncertain_entries` 段（2026-09-02 起）= 存疑映射，含 `tentatively_mapped` / `misprint` /
    `unverified` / `user-confirmed-closed` / `resolved-notfound`，附 `reason` + `next_action`；
    命中按 `next_action` 复核，不重复误判。

## 4. 归一化规则（须完整实现，漏剥后缀会误判）

去空白/全角空格、小写、全角括号转半角、剥通用后缀：
`量贩ktv / 歌舞厅 / 演艺大舞厅 / 音乐舞厅 / 娱乐厅 / 交谊舞厅 / 交谊舞 / 大舞厅 / 音乐茶楼 /
音乐吧 / 歌舞城 / 大众舞厅 / 舞厅 / 酒吧 / 俱乐部 / club / ktv`。

- ⚠️ 「交谊舞」**须单独成后缀**（2026-09-01 实测漏剥导致「永乐交谊舞」被判 CONTAINED 而非 EXACT
  ——「永乐交谊舞」=「永乐舞厅」实为同一家）。
- ⚠️ **装饰性分隔号必须剥离（2026-09-18 新增，`norm()` 末行）**：`· ・ • . ~ ～` 在店名里纯装饰，
  不剥会让「全等 / 去后缀 / 包含」**三道同时失效**——平台「新·合·富舞厅」vs 舞讯「新合富」：
  全等 ✗（字符集不同）、去后缀 ✗、包含 ✗（两侧都嵌不进对方）⇒ 真店被判 UNMATCHED 进表③
  （**假新店**），且真身 #1207 的 SUSPENDED 没人恢复（**两个方向同时错**，比漏匹配更贵）。
  实现：`re.sub(r"[\s\u3000·・•.~]+", "", s)`（在全角转半角**之后**执行，`～` 已先变 `~`）。
  ⚠️ 短横 `-`（如「鎏金-铂金翰娱乐会所」）**刻意未纳入**剥离集——少数店名里它是语义的一部分。
  平台现有 17 家店名含分隔号，去号后**同城无新增碰撞**（唯一碰撞 = 绍兴「邂逅音乐吧」本就有
  两家重复条目 #1080/#1083，与本次改动无关）。
  改动前后必须用**同一份 export 快照**跑回归比对（09-14 立规）：
  2026-09-18 回归 = 163 条 mention 中仅 1 条变动（沈阳·新合富 UNMATCHED → EXACT #1207），符合预期。
- 名称含括号时，括号**内的别名**也要作为独立 key（「蓝堡舞吧(蓝钻)」→ `蓝钻`）。
- ⚠️ **繁简 / 异体字不在 `norm()` 的处理范围（2026-09-23 新增）**：`norm()` **不做繁简转换**，
  源一旦用繁体写法，**全等 / 去后缀 / 包含 / 首二字子串 / 形近字五道全部失效**。
  实证 09-23：市井慢时光摘要与 xianbao360 正文都写**「櫻花」**（繁体），平台门店是「樱花娱乐」
  ⇒ keyword「櫻花」0 命中 → 落表③「假新店」；同时真身 #422 因「未被点名」落进表⑤′
  （**两个方向同时错**，与 09-19「金池天/汇影秀」、09-20「新富合」、09-21「帅喵」同型，已是**第 4 例**）。
  **判据**：UNMATCHED 条目进表③前，先做一次**简繁对查**——把繁体写法转简体再 keyword 一次
  （或直接查同城平台的简体同名/近名），命中即按 `variant` 双写。
  已知适用样本：樱/櫻、柏/栢（金栢丽 → #177 金柏音乐酒吧）、丽/麗（雲麗）、云/雲。


## 5. 比对要点（逐条）

- **同名不同城 = 两家店**，必须同城过滤（2026-09-04 险些把滁州 4 家错归马鞍山）。
- **县级 header 回挂母城（2026-09-11 实证）**：舞讯把县级行政区独立成 header（江阴/昆山/句容/
  丹阳/海宁/仁寿）时，平台里这些门店挂在母城名下（city=无锡市/苏州市/镇江市 + district）。
  ① 匹配候选集必须**回挂母城并按 district scope 过滤**（否则喜见/K2/金佰莉全误判 UNMATCHED，
  其 OPEN 正本反落表⑤被误暂停——09-11 镇江 3 家险误伤）；② **M 统计必须直接用命中源集合**，
  不得按「平台城市 ∈ 源覆盖城市」过滤——县级 header 点名会被该过滤丢掉（09-11 汇锦/盛邦/
  星夜之约/繁花四家 M 被清空，星夜之约/繁花本该进表①反转）。
- **地址维度**：舞讯带地址时与候选 address/district 交叉验证；同城同名但地址迥异的两家店，
  不能因同名就命中——以地址为准降置信。
- **每个 opening 允许多命中**（粘连 token），取置信度最高者为主命中，其余列备注。
- **UNMATCHED 兜底第一道 —— 首二字子串（2026-09-04 实证 8/10 归位）**：用「首二字子串 + 长度差 ≤6」
  搜同城候选，错字/异体/括号别名基本一搜一个准（金卡乐→金卡罗、星曜乐→星耀乐、
  玛莎→富都汇（玛莎嗨嗨）、随圆→随园）；归位后按 typo/variant/alias 回写字典，别急着进表③。
- **UNMATCHED 兜底第二道 —— 形近字（2026-09-10 新增）**：首二字子串**兜不住「同音/形近但首字
  不同」的错字**——`熠潮↔煌潮`、`阑夜↔澜夜` 首字不同，一律搜不到、被误判 UNMATCHED。
  补规则：**同城 + 名称等长 + 末字相同 + 同城候选唯一（或唯一还没被别的点名占用）→ 判 typo 归位**。
  漏判代价不是「少匹配一条」，而是**该店被当成新店进表③建档**（或反过来落进表⑤被误暂停）。
- **UNMATCHED 兜底第三道 —— keyword 交叉验证必须前置（2026-09-14 新增）**：前两道都建立在
  「长度差 ≤6」和「包含度 ≥ 阈值」上，**短名点名长名店时会双双失效**。09-14 实证：成都「王者」
  → #1150 **王者台球莎莎舞俱乐部**（长度差 8 > 6、包含度 2/10 = 0.20 < 0.34）→ 两道都判 UNMATCHED。
  → 口径修正：**每条 UNMATCHED 在进表③/表④之前必须先做一次 `GET /venues?keyword=<名>`
  交叉验证**（原来只在「怀疑假新店」时才做）；判据 = 同城候选里存在唯一「含该短名」的门店即归位，
  置信度记 CONTAINED。否则「新店候选」里会混进平台早就有的店（进而触发误暂停/误建档两个方向）。
- **短前缀空格勿拆**：「es 星海壹号」「ls丽莎」「M莎莎」类「字母/数字前缀 + 中文」之间的空格
  通常是同一家店的前缀标记，按一家处理（两种写法都录入匹配，同命中一家即合并）。
- **同城命名家族模式**：南宁「XX舞汇」系（舞讯写短名 乐舞/欢舞/海角/天涯/天籁…）下短名 ⊂ 长名
  是常态，批量 CONTAINED 属预期（多为已 OPEN 进表④，不逐条问）。
- **「原X」= 更名线索（2026-09-08 起）**：舞讯带「梦都（原传奇）」「泓酒汇（原芭莎）」「喜见（原芭黎人）」
  「老朱（原夜猫）」等括号原名时，先查平台原名店现状（常已存在且 OPEN / 平台名已带别名括号），
  命中后按 `renamed` 登记并可询问用户是否同步 `updateVenue` 更名；平台名已含别名则零动作。
- **粘连 token 拆分**：「蓝月千里缘」=蓝月+千里缘、「虹光天天和」=虹光+天天和、「食品华新」=食品+华新、
  「金笑夜色」=金笑+夜色、「乐8新艺城」=乐8量贩ktv+新艺城。
- **多源错别字差异**：蜀尔顿/爵尔顿、菲利/菲琳、蓝钻/蓝堡舞吧(蓝钻)——靠字典 + 平台名自带别名括号归位。
- **removed_duplicates 命中先查正本（2026-09-04 实证）**：当时删的是重复份，正本可能仍在库且 OPEN
  （长沙 913/919/934）——先搜同城同名，有正本按正常流程处理，无正本才跳过。
- **LLM 语义兜底**：错别字/谐音/简称/方言名规则覆盖不到时用语义判断，但必须在汇报里给出
  「为什么认为是同一家」的依据；低置信一律归 CONTAINED。

## 6. 别名回写（2026-09-08 起，写库确认后的固定动作）

本轮确认的 typo / alias / variant / renamed / 括号拆分出的曾用名 → **双写**：

1. 平台别名字段 `POST /admin/venue-aliases/batch-import`（运行时权威，搜索/比对/详情即时生效）；
2. 本 Skill 字典 `entries`（经验沉淀 + 平台缺失时兜底）。

两层缺一不可。逐条幂等（同店同名有效行 skipped、软删行复活、单条失败不拖累整批）；别名与主名
同名自动跳过。**09-10 实证**：`熠潮→煌潮舞厅(#1152)`、`阑夜→澜夜酒吧(#1173)` 双写完成。

### 6.1 低置信长尾的别名化（2026-09-25 立，用户拍板）

**问题形态**：平台店名带**舞讯没有的后缀**、或后缀是**错字变体** ⇒ 第 3 层「去后缀精确」失效
⇒ 一路退到第 5 层首二字兜底 ⇒ 判 `CONTAINED` ⇒ **每轮都要人工过一眼**（同一形态反复挂表②，
累计 5 轮的重复劳动）。

**两条路的辩证对比**（2026-09-25 用户裁决；此前 Skill 连续 4 轮只是把两个方案并列列出、未拍板）：

| | A 扩 `SUFFIX` 词表 | B 加别名（✅ 采用） |
|---|---|---|
| 影响面 | **全库杠杆** —— 加「音乐茶吧」改变所有城市的剥后缀行为，须全量回归验证无新碰撞 | **一店一行**，改动可枚举、可审计 |
| 语义 | 机械规则（可能把某店名剥成单字或制造撞名） | 明确的身份事实（该店的俗称/写法） |
| 可逆性 | 回滚 = 改代码 + 重跑批 | 回滚 = 软删一条（`DELETE /admin/venue-aliases/{id}`） |
| 附带收益 | 无 | **用户搜索也命中**（`KW_MATCH` 别名分支）+ 详情页身份核验位 |
| 覆盖 | 一次覆盖整族 | 只覆盖被点名的店（实测：整族里需要加的恰是那几家） |
| 代价 | 误伤不可枚举 | 长尾逐个补（维护量 = 被点名的店数） |

⇒ **判据：长尾一律走 B。`SUFFIX` 词表保持稳定，只在「确属通用后缀 + 全量回归证明安全」时才动。**
（⚠️ 这条推翻了本 playbook 与 SKILL.md 此前并列给出的「方案 A」——原方案 A 作废，勿再复述。）

**两个已闭合实证（完全同型）**：

| 店 | 舞讯写法 | 失效原因 | 别名 | 结果 |
|---|---|---|---|---|
| #978 颐和音乐茶吧 | 颐和 | 词表有「音乐茶楼/音乐吧/音乐酒馆」**独无「音乐茶吧」** | 颐和 | `alias-domain:颐和` → EXACT |
| #1167 K2聚乐部 | k2 | 平台名把「俱乐部」写成**「聚乐部」**（错字变体） | k2 | `alias-domain:k2` → EXACT |

#978 的时间线值得记住：**09-18 起断续出现，09-19/20/23/24/25 连续 5 轮落表②**——
每一轮都靠人工确认「这家是正常的」，而根因（词表缺一个后缀词）一直没被处置。
**教训 = 同一形态第 2 轮就该固化掉，不要等用户第 5 次回答同一个问题。**

**⚠️ 边界（别滥用）**：
- 别名取值 = **舞讯的原写法**（匹配器是拿舞讯写法去别名域查表），**不是**推测的店名；
- 🚫 不为「包含式误挂」补别名——那是匹配错误（`contained:*` 挂到了别家店上），该修匹配；
- 🚫 不为**新店候选**补别名（新店走表③ 放行建档，红线 4）；
- 登记后**必须重跑 `qw_match.py` 回读验证** `via=alias-domain:*` —— **没验证等于没做**
  （若仍非 EXACT ⇒ 别名写法本身不对）。升为 EXACT 后自动进表①（`M==S + 高置信`），
  按既有口径**自动反转 + 自动发公告**，收口闭环。
