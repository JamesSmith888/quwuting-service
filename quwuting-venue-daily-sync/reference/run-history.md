## 真实事故与复盘

### 菲琳 / 玫瑰天堂「明明营业却显示停业」

平台快照为 CEASED 而实际已 OPEN，用户投诉。→ 催生「每日跟进舞讯、状态保鲜」这条主线，
以及「门店时效性基本是一天当天的」口径。

### 2026-09-01 · 翻页漂移导致 10 家「假新店」

`searchRanked` / `searchRankedNoLocation` 的 `ORDER BY HEAT_SCORE DESC` 无 id tie-break，
热度分大量为 0 时排序键重复，翻页边界漂移——实测 recommended 翻页拉成都 107 家只返回 81 家
（漏 26 家），连带误判 10 家「假新店」。修复 = 两个排序补 `, v.id DESC`；export 的
`findExportPage` 用 `id ASC` 天然稳定。**教训已写进 SKILL.md**：候选拉取必须稳定排序。

### 2026-09-04 · 滁州 4 家险归马鞍山

全量拉取后未核对平台城市词表，险些把平台未覆盖的滁州条目混入邻近的马鞍山比对。
→ 立规：**全量拉取后必须用 `GET /venues/cities` 核对，平台未覆盖城市的舞讯条目剔出比对集**。

### 2026-09-08 · 昆山新茶吧 #1114 单源反转回退

仅 C 源点名即执行反转，事后回退。→ 催生 09-09「单源不写库」红线（系统性收口），
09-10 进一步收紧为「全源一致」。

### 2026-09-10 · 城市名口径未归一（静默失败）

A 源「成都/重庆」vs B 源「成都市/重庆市」，`covered` 求交为 ∅ → 双源被判单源 → 成都/重庆**整城
静默跳过**（不报错）。修复 = 统一去「市」归一；成都补出 3 家暂停。→ 立规：**提交前打印各城 S 分布自检**。

## 2026-09-14 · 人工权威层级门禁（V25，**口径级变更，非跑批实录**）

**触发**：用户提出「别人的舞讯不一定准确 ⇒ 管理员手动改过的状态不能被每日舞讯覆盖；
但人工改的过段时间也会不准，还是要以舞讯为准」。

**结论（方案三选一，取「人工锁 + 永久豁免」）**：把优先级**下沉为服务端领域不变量**，
不在本 Skill 侧维护黑名单（理由：Web 后台在同步报告里勾选应用走的是另一条入口
`VenueSyncReportService → applyBatch`，Skill 侧管不到；且「锁会过期」的时间语义
在字典里无处安放）。

**对采集侧的三条硬约束（写进 SKILL.md 主体）**：

1. **不自己判门禁**——判定唯一实现在服务端 `VenueStatusGuardService`；
   export 新增的 `statusSource` / `statusLockedUntil` / `dailySyncExempt` / `syncNote`
   只用于差异表**标注**与交叉核对，禁止据此再算一遍（两处逻辑必然漂移）。
2. **如实汇报跳过**——两个批量通道返回体新增 `skippedLocked` / `skippedExempt` / `skipped[]`；
   必须单列一行，**不得**混进「暂停 K 家」或笼统的「跳过 X」。
   理由：门禁跳过是**机制在工作**，混进去用户会判定为漏跑。
3. **禁止经 `POST /venues/{id}/update` 改状态**——那是人工编辑通道，会打人工锁；
   Agent 若需要（CLOSED→OPEN 恢复营业）必须带 `"changeSource":"AGENT_BATCH"`，
   才被判为外部通道并受门禁约束（被拦时资料照改、状态不动）。

**锁机制要点（供理解汇报口径）**：人工置 OPEN 锁 3 天 / 置停业类 7 天（运营可配，
`venue.status_lock.*`）；锁到期自动回归自动同步；`CLOSED` / `RENOVATING` 天然免疫
（两个外部通道只动 OPEN↔{CEASED, SUSPENDED}）；反复冲突的店应升级为**永久豁免**
而非加长锁。**明确不做**历史回溯（会把几个月前的一次性人工修正全锁上）。

**关门方向口径不变（用户 2026-09-14 确认保留）**：「≥2 源覆盖该城才自动写库」的多来源
确认门继续生效；「未提及即关门」是**语义**，不是跳过确认门的授权。

**平台侧落地**：V25 迁移 + `VenueStatusGuardService` + 三个管理端接口
（`/admin/venue-sync/guard/{query,unlock,exempt}`）；权威文档 `docs/agents/48`。
