## 2. 当前分发规则（速览）

> 🔴 **默认形态 = 一条合并公告（2026-09-18 起）**：【恢复营业/状态更新】段在前、【新增门店】段在后。
> 「新增独立成条」已作废。

| 情形 | 公告 |
|---|---|
| 🔴 表①（高置信开门）写库成功 | **永远直接 create+publish，不询问**（09-15 起；单源日亦然）；进入合并条的【恢复营业】段 |
| 表②（低置信/冲突）**用户逐条放行**后写库 | **数据放行后仍须询问**是否发公告；发出时同样进【恢复营业】段 |
| 表③（新店）**用户放行建档后** | **不再独立成条**（09-18 起）⇒ 进当日合并条的【新增门店】段；数据放行后仍须询问是否发公告 |
| 高置信但平台已 OPEN（当日零写库） | **直接发**「确认营业门店」版式（09-17 用户授权，不再询问） |
| 表⑤（关门/暂停） | **不发**（纯噪音；暂停只写库 + 通知关注者） |
| 单源新店录入 / 混合批次 | **询问用户**后发；形态同上（更新在前、新增在后） |
| 零新增零恢复（= 当日零写库） | 同上一行第 4 条：用「确认营业门店」版式（见 §5） |


## 3. 发布前检查（固定动作）

1. `GET /admin/announcements?page=0&size=10` 扫一眼列表——看今天是否已有 DATA_UPDATE；
2. status 取值 `DRAFT / PUBLISHED / OFFLINE`；**OFFLINE 与昨日 PUBLISHED 均无碍**，直接 create+publish；
3. **仅当今日已发且信息不全（PUBLISHED）** → 先 `POST /admin/announcements/{旧id}/offline` 下线旧条，
   再 create + publish（09-06 实证：#18 与晚间 52 家新店合并为 #19，offline #18 → create #19 → publish）；
4. 接口链路：`POST /admin/announcements/create`（body `{title, content, category:"DATA_UPDATE", pinned?}`）
   → `POST /admin/announcements/{id}/publish`（缺省立即发布）。管理端 Web 后台「公告管理」同链路。
5. **不用传 `touchLevel`（2026-09-15）**：`DATA_UPDATE` 由后端按 category 派生为 `SILENT`
   （不打扰、不计入用户未读）。⚠️ **每日舞讯不得显式写 `"touchLevel": "ALERT"`**——
   那会让它重新开始点亮用户的未读徽标（09-15 修的就是这个）；同理，只有当公告语义
   与分类缺省相反时才显式传该字段。

**询问话术**：汇报完成后附「**是否发一条公告？**（标题按内容主体选：主为新增门店如『X月X日新增N家门店』，含恢复营业如『X月X日舞讯更新』）」；用户确认后执行
create+publish（本地 develop 也照做，用户确认即视为授权）。用户未确认 → 不创建公告。

**应急处置 · 已发布多条公告需合并/重组（2026-09-18 实证）**：
顺序必须是「**先 create+publish 新条 → 再逐条 `offline` 旧条**」，**反向操作会留下用户可见的空窗**。
不要试图 `update` 旧条去承载另一条的内容（`update` 只用于修正原公告自身错误）——
两条来源无法原地合并，且改写已发布内容会让已读用户的记忆与线上不一致。
⚠️ 合并只在**用户明示**时做（默认仍按分开制）；合并后 `GET /admin/announcements` 复核
「PUBLISHED 的 DATA_UPDATE 是否只剩预期的那些」，并把 OFFLINE 的旧 id 记进 run-history。

**两种合并形态（2026-09-18 补齐，勿混用）**：

| 形态 | 场景 | 范围来源 |
|---|---|---|
| **同批合并** | 同一次跑批里【新增】与【恢复】被要求并成一条（先例 #57） | 本批数据 |
| **跨批合并** | 当日早先批次遗留未公告的门店，一次性并进终态条（先例 **#62**：天津当日 3 批 25 家 + #61 原内容） | **须用户当轮显式指定范围** |

🔴 **跨批合并的口径边界**：它是**用户当轮指定范围**的结果，**不构成「前批默认可后补」的授权**——
默认可公告集合恒 = **用户明确放行的那批**。前批若被明示「暂不发」，未经用户改口**不得自动补进**公告，
即使后续批次被要求发布（实证：天津前两批 20 家是在用户本轮明确选「今日 25 家全并」后才纳入的）。
⛔ 反向也成立：**不得因「今日已有一条公告」就把新批自动并进去**——是否发布、并入哪些，仍须按
§2 分发规则询问或依据用户既有授权。

⚠️ **合并/下线前必须先扫「全天」而不是「本轮」**（2026-09-18 实证）：
用 `GET /admin/announcements?page=0&size=20` **按 `publishAt` 过滤当天**逐条核对，
**不要只按自己本轮创建的 id 范围操作** —— 当日早批由**自动链路**（表① 高置信写库后自动发布）
产生的公告不在本轮 id 里，漏掉就会留下两条内容重叠的置顶公告
（实证：第一轮合并时漏了 14:34 自动发的 #54，用户追问「18 号不是还有一个公告吗」才补并）。
判定范围 = **当天 × `category=DATA_UPDATE`**；`NOTICE` 等其它类目一律不动（如当日的运营通知 #53）。

## 4. 模板与渲染细则

> 🔴 **段序 = 【恢复营业】在前、【新增门店】在后（2026-09-18 用户拍板，长期口径）**。
> **标题**（2026-09-18 用户确认「标题没问题，只是内容换位置」⇒ **合并条标题沿用「新增在前」形态**）：
> 两者都有 → `{M}月{D}日新增{N}家门店·恢复{M}家`；仅新增 → `{M}月{D}日新增{N}家门店`；
> 仅状态更新 → `{M}月{D}日舞讯更新`。同日标题冲突加 `·` 后缀区分（先例 #48）。

```
【恢复营业 {M} 家】
- [门店名](venue://<venueId>)（城市·区县，可附状态/备注）
- …

【新增门店 {N} 家】
- [门店名](venue://<venueId>)（城市·区县[，暂停营业]）
- …

以上门店点击可直接查看详情，营业状态以现场实际情况为准。
```

- **门店可点击链接 = `[店名](venue://<venueId>)`**（2026-09-03 前端已支持；能力见
  `docs/agents/34「正文链接」` + 小程序 `utils/announcementLinks.ts`）：归一化 `venue://12` → 详情页
  路径，towxml 渲染为 navigator 直达；外链/未知协议自动降级纯文本。
- 分组文案可选「新增门店 / 恢复营业 / 状态更新」；**仅一类门店时只列存在的分组标题**；
  今日停业等非 OPEN 的新增店也列出并在括号注明（如「苏州昆山，今日停业」）。
- **大批量（≥10 家跨多城）按城市分组渲染**（09-06 54 家实战 #19）：

  ```
  **城市名**（N 家）
  - [店名](venue://id)（城市·区县[，状态]）
  ```

  停业店统一注「，暂停营业」、OPEN 不注——比 50+ 行平铺更可读。城市小标题须用全称（滁州市），
  与门店括号内简称（滁州·来安县）并存不冲突。

## 5. 「确认营业门店」版式（2026-09-10 用户拍板，零新增/零恢复时）

当本轮零新增零恢复、但用户仍要发公告时，改为**列「全源一致确认营业中」的门店**：

- 标题不变（`{M}月{D}日舞讯更新`，DATA_UPDATE，pinned=true）；
- 正文首句：「今日已核对各来源舞讯，以下 **N 家门店**经两个来源共同确认今日营业中（按城市分组）：」
- 城市分组渲染（同 §4）；
- 结尾：「以上门店点击可直接查看详情。营业状态随时变动，以现场实际情况为准。」
- ⚠️ **口径必须写「两源共同确认」**，不能写成「全部营业门店」——与「未上榜即暂停」的关门口径
  会自相矛盾。

**09-10 首跑实证**：148 家 / 22 城，公告 #27（本地 develop）。

**09-17 单源日分叉（口径补充）**：单源日零写库仍要发公告时，**首句不得写「两个来源共同确认」**
（事实不符，单源就是单源）→ 写「今日已核对舞讯，以下 **N 家门店**今日营业（按城市分组）：」，
结尾同本节的「以上门店点击可直接查看详情。营业状态随时变动，以现场实际情况为准。」

- **名单只取高置信**：`confidence ∈ {EXACT, ALIAS}` **且平台 status = OPEN** 的命中店
  （09-17 实测 118 家 / 23 城，公告 #51）。
- ⚠️ **CONTAINED 低置信绝不入公告**：包含式匹配会把「成都·金卡」挂到「#444 金卡罗歌舞城」这类
  **不同店**上，写进公告等于对用户做未经证实的断言。低置信命中店照常计入「已点名」（因而不会被暂停），
  只是不进公告名单——**这两个集合的口径不同，别混**。
- 城市排序按门店数降序（热点城市在前），同数按城市名；城市小标题用全称（`成都市`），
  门店括号内用简称+区县（`成都·金牛区`）。
