# PG → MySQL 迁移可行性分析

> 评估日期：2026-08-30
> 范围：quwuting-service 后端（Spring Boot 4.1 / Java 25 / Hibernate / Flyway 12）
> 结论：**可迁移，但非"改配置即跑"**。硬绑定集中在 2 类（并发 advisory lock、日期骨架），其余为机械性方言改写。

---

## 一、结论摘要

| 维度 | 评估 |
|---|---|
| 业务代码（Service/Controller） | ✅ 基本无绑定，JPQL/Spring Data 标准用法为主 |
| 实体映射 | ✅ IDENTITY 主键策略天然契合 AUTO_INCREMENT |
| 原生 SQL（@Query nativeQuery） | ⚠️ 60+ 处，其中 ~15 处含 PG 特有语法需重写 |
| 迁移脚本体系（V1–V61） | ❌ 61 个脚本全为 PG 方言，需重建 MySQL 基线（勿逐脚本翻译） |
| 并发控制 | ❌ `pg_advisory_xact_lock` 6 处，MySQL 无事务级等价物，需重新设计 |
| 平台依赖 | ⚠️ Supabase Storage 直传与 DB 解耦，可保留；RLS 脚本仅 Supabase 侧有效 |
| 总体工作量 | 约 3–6 人日（含数据迁移与回归验证） |

## 二、硬绑定清单（按改造难度排序）

### Tier 1 — 并发控制（需重新设计，不能机械替换）

`pg_advisory_xact_lock` 是 PG 独有的**事务级**咨询锁（事务提交/回滚自动释放）。MySQL 的 `GET_LOCK(name, timeout)` 是**会话级**锁，且必须与业务在同一物理连接上执行、异常路径需手动 `RELEASE_LOCK`——HikariCP 连接池下直接替换极易死锁/漏锁。

| 位置 | 用法 |
|---|---|
| `venuereaction/repository/VenueReactionRepository.java:71` | `pg_advisory_xact_lock(hashtext(:lockKey))` |
| `dancer/repository/DancerRecognitionRepository.java:23` | `pg_advisory_xact_lock(hashtext(:lockKey))` |
| `points/repository/PointsTransactionRepository.java:117` | `pg_advisory_xact_lock(hashtext(:lockKey))` |
| `points/repository/PointsUnlockRepository.java:26` | `pg_advisory_xact_lock(hashtext(:lockKey))` |
| `points/repository/DailyCheckinRepository.java:27` | `pg_advisory_xact_lock(hashtext(:lockKey))` |
| `venuestatusreport/repository/StatusReportRepository.java:79` | `pg_advisory_xact_lock(CAST(:uid AS bigint)*1000003+CAST(:vid AS bigint))` |

**建议替代**：优先收敛到"唯一约束兜底 + 幂等 upsert"模式（项目已有 `ON CONFLICT DO NOTHING` 先例，V21/V29 定则）——每日一记/首报类逻辑本身就有 UNIQUE 约束，冲突时 INSERT 幂等即可，去掉锁；确需串行化的场景（积分对账）再评估 `SELECT ... FOR UPDATE`。

### Tier 2 — 日期骨架与聚合（重写但直接）

PG 用 `generate_series` 生成连续日期骨架实现"天然补零"，MySQL 无此函数。

| 位置 | PG 写法 | MySQL 替代 |
|---|---|---|
| `venue/repository/VenueRepository.java:742-789`（countDailyTrends） | `generate_series(...)::date` + `date_trunc('day', created_at)::date` + `interval '1 day'` | `WITH RECURSIVE` 日期序列 + `DATE(created_at)` + `INTERVAL 1 DAY` |
| `dancer/repository/DancerStatsRepository.java:241-279`（countDancerDailyTrends） | 同上 | 同上 |
| `DancerStatsRepository.java:268-271` | `COUNT(*) FILTER (WHERE source='LIST')`（MySQL 8 不支持 FILTER） | `SUM(CASE WHEN source='LIST' THEN 1 ELSE 0 END)` |
| `DancerStatsRepository.java:387` | `CROSS JOIN LATERAL unnest(string_to_array(d.service_ids, ','))` | `JSON_TABLE()` 或 Java 侧拆分 |

注意：`CAST(... AS timestamp)` 在 MySQL 需改为 `CAST(... AS DATETIME)`；`::date` 改 `CAST(... AS DATE)`。时区上 PG 的 timestamptz 重载坑（2026-08-08 统计图全空事故根因）在 MySQL 无时区 datetime 下反而消失。

### Tier 3 — 语法点改写（机械性，有验证机制可兜底）

| 位置 | PG 语法 | MySQL 替代 |
|---|---|---|
| `dancer/repository/DancerPhotoRepository.java:45` | `SELECT DISTINCT ON (p.dancer_id)` | `ROW_NUMBER() OVER (PARTITION BY dancer_id ORDER BY ...)` 外层过滤 rn=1 |
| `recruitment/repository/RecruitmentContactFetchRepository.java:23` | `INSERT ... ON CONFLICT (a,b) DO NOTHING` | `INSERT IGNORE`（注意会吞非唯一冲突错误，慎用）或 `ON DUPLICATE KEY UPDATE id=id` |
| `venue/repository/VenueRepository.java:610,875,879,885...`（findHotVenueIds） | `CURRENT_DATE - 30` / `CURRENT_DATE - 7`（native 裸整数减法） | **必须改 `DATE_SUB(CURRENT_DATE, INTERVAL 30 DAY)`**——MySQL 中 date−integer 是数字运算（20260830−30=20260800），**静默产出错误日期而非报错**，比语法错误更危险 |

> ⚠️ 特别提醒：JPQL（非 native）中的 `CURRENT_DATE - 30 day` 是 HQL 语法，Hibernate 会按方言正确翻译（PG: `- 30`，MySQL: `DATE_SUB`），**安全**；只有 native SQL 里的裸整数减法危险。

### Tier 4 — 迁移脚本体系（最大工程面，建议整体重建基线）

61 个脚本（V1–V61）全部是 PG 方言，且 V51–V61 已落库（字节纪律约束现有 PG 库）。**正确策略不是逐脚本翻译，而是对 MySQL 环境重建基线**：

| 语法 | 涉及脚本 | MySQL 替代 |
|---|---|---|
| `bigint GENERATED BY DEFAULT AS IDENTITY`（21 个建表脚本） | V1 及全部建表 | `bigint AUTO_INCREMENT` |
| `ALTER TABLE ... ALTER COLUMN x TYPE ...` | V60/V44 | `MODIFY COLUMN x type` |
| `ALTER COLUMN x SET/DROP NOT NULL` | V6/V11/V42 | `MODIFY COLUMN x type [NOT NULL]` |
| `DO $$ ... END $$` plpgsql 匿名块（防御校验/数据清洗） | V3/V5/V15/V16/V37 | 存储过程 + CALL，或纯 SQL 校验 |
| `CREATE OR REPLACE FUNCTION ... LANGUAGE sql IMMUTABLE` | V38（qwt_city_key） | `CREATE FUNCTION ... RETURNS ... DETERMINISTIC` |
| `LATERAL jsonb_array_elements_text(...) WITH ORDINALITY` + `::jsonb` | V35 | `JSON_TABLE()` |
| `jsonb_agg` / `jsonb_build_object` / `to_char(...,'HH24:MI')` / `@>` | V5 | `JSON_ARRAYAGG` / `CONCAT` 组装 / `DATE_FORMAT` / `JSON_CONTAINS` |
| `CURRENT_TIMESTAMP` / `NOW()` | V41/V35 | 两库均支持（兼容） |

**建议执行路径**：
1. 从现有实体映射 + 线上库结构反向生成 1 份 MySQL 全量 DDL（新 V1 基线）；
2. MySQL 环境 Flyway `baseline-on-migrate`（配置已就绪，见 application.yaml）跳过历史脚本；
3. 数据迁移：`pg_dump` 导出 → 类型映射（boolean→tinyint(1)、timestamp(6)→datetime(6)、double precision→double，JSON 字符串列原样无损）→ `mysql load`；
4. 业务代码只修 Tier 1–3 的 native SQL。

## 三、可移植性良好（迁移阻力小的部分）

- **ID 策略**：全表 `GenerationType.IDENTITY`，MySQL AUTO_INCREMENT 完美契合（含 SchemaIntegrityChecker 的 identity 校验契约）。
- **dialect 未硬编码**：application.yaml 无 `hibernate.dialect`，Spring Boot 自动探测；pom.xml 已声明 `mysql-connector-j`（runtime），只需补 `flyway-database-mysql` 依赖。
- **SchemaIntegrityChecker**：`getDatabaseProductName()` 判断非 PostgreSQL 自动跳过（config/SchemaIntegrityChecker.java:62-64），不阻塞启动。
- **无重绑定对象**：无触发器 / 序列 / 扩展（pg_trgm 等）/ 物化视图 / 分区表 / 自定义类型 / 存储过程（除迁移脚本内嵌）。
- **JSON 存储克制**：tags/photos/business_hours/tickets/partner_fees 均为 varchar 字符串列（序列化 DTO），无 JSONB 语义依赖。
- **native SQL 中大量标准 SQL**：GREATEST/COALESCE/CASE/窗口函数（ROW_NUMBER/COUNT OVER）等 MySQL 8.0 均支持（如 UserRepository findPageByFiltersOrderByLastActive、VenueRepository findHotVenueIds 的窗口部分）。
- **测试无强依赖**：单元测试未用 Testcontainers，无 @Sql 脚本；`-Drun.db.tests=true` 原生 SQL 验证机制可在 MySQL 环境复用。

## 四、平台级考量（超出 SQL 语法）

1. **Supabase Storage 直传**：前端 `miniprogram/services/storage.ts` 直传 + 后端签发凭证，与 DB 完全解耦——DB 迁 MySQL 后 Storage 可继续用 Supabase；若目标是完全脱离 Supabase，对象存储需换（如阿里云 OSS），前端上传 + 后端鉴权要重做。
2. **RLS 策略**：`scripts/fix_rls_dancer_videos.sql` 等 RLS 脚本是 Supabase 平台能力，MySQL 无对应物；继续用 Supabase Storage 则无影响。
3. **性能**：现 DB 在东京（单次往返 300–500ms，性能第一约束）；若 MySQL 自托管在阿里云 ECS（114.55.0.14）同区，延迟反而大幅改善，连接池/Hikari 调优参数可保留。

## 五、工作量评估

| 工作项 | 工作量 | 风险 |
|---|---|---|
| 并发控制重构（advisory lock → 唯一约束/FOR UPDATE） | 1–2 人日 | 高（需逐场景验证幂等性） |
| 日期骨架 + FILTER + LATERAL 重写 | 0.5–1 人日 | 中（口径回归：趋势图补零） |
| Tier 3 语法点改写 | 0.5 人日 | 低（-Drun.db.tests 可验证） |
| MySQL 基线 DDL + 数据迁移 | 1–2 人日 | 中（数据量小，类型映射简单） |
| 回归验证（列表/统计/积分/打卡/认可/举报/招工） | 1 人日 | — |

**总体：3–6 人日。** 主要风险不在语法而在**并发语义**（Tier 1）与 **MySQL 静默语义差异**（date−integer），建议迁移时对统计口径和积分/打卡并发做专项回归。
