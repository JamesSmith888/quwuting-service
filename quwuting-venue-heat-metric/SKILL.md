# 门店热度/排序指标：提案评估与落地

## 一、先过四问判据（任一不过 → 不进排序层）

用户提的候选指标，先逐条筛。**四问不过就不进 `HEAT_BEHAVIOR`/`HEAT_SCORE`**，最多做展示字段。

| # | 问题 | 不过的后果（均有生产实证） |
|---|---|---|
| 1 | 与既有项**条件独立**吗？ | 只是加权放大器。09-01 收藏「总数×10 + 新增×15」是集合包含关系，一次收藏双计 25 分 |
| 2 | **单位**是什么？有 `(user, venue, day, type)` 唯一键吗？ | 必被刷，且运营自己会刷（crowd report 因此拍板零积分） |
| 3 | 随**曝光量线性增长**吗？ | 复现马太闭环（08-27 线性 PV 的教训：排序→曝光→浏览→排序） |
| 4 | 是**门店需求**信号，还是**产品体验/信息完备度**信号？ | 把产品做得差当成店火 |

**2026-09-19 浏览项改人数口径（现行，勿再按 ln 压缩提案）**：
`浏览贡献 = 近30天去重浏览人数×0.30 + 近7天去重浏览人数×0.40 + ln(1+近30天匿名浏览行数)×1.00`。
旧口径 `ln(1+Σ(来源权重×时效因子))` 实测封顶仅 **6.4 分**（< 1 次收藏的 8 分）——把"有多少人
来看"和"被点开多少次"混在一起压，结果是**排序由最稀疏的信源主导**（332 家「有人看、0 收藏」
的门店在排序中无法体现；111 家有收藏的门店里 89 家恰好 1 人 = λ≈1 泊松噪声）。
**来源权重（LIST 0.5/SEARCH 1.5/SHARE 2.0）随之退出公式**（来源仍采集、趋势图照常展示）。
改后：抖舞 6.3→59、丽莎 6.4→56.4、约翰 4.9→34；热门集合 4→5 家。
**真实收益是抗扰动性**（1 次收藏 8 分不再能改排序，需 ≈20 UV 等效），**不是换榜**。
**未解决**：只改浏览口径不治游戏面（约翰仍 143 第 2，收藏 64 分主导）→ 仍需「人气基数门槛」。

**已裁决的历史结论（勿重复提案）**：
- 分享门店：`ViewSource.SHARE ×2.0`（分享卡片被打开）已在奖励传播；再把 `qwt_venue_shares` 的 SHARE 动作计分 = 发起端 + 接收端**双计**。若要用，必须按 `channel` 分权（TIMELINE 偏推荐 / MENU 偏邀约）并先扣除重复计量。
- 发起导航：`wx.openLocation` 跳出小程序到微信内置地图，**拿不到"是否真的导航/到达"回调**，只能记"点了按钮"，含大量"看看离多远然后放弃"的动作。
- 复制地址/名称：**出口行为**，语义不可判（推荐/质疑/存档），且与"信息不完备"正相关——计分 = 奖励产品缺陷。
- 页面停留：衡量页面体验而非门店需求；小程序伪停留（前后台切换/锁屏/长挂后台）不可采。
- **取消收藏不需要单独进公式**：`favrecent` 带 `f.deleted = false`，而取消走软删 → 自动移出计数 = 自动 −8，净额效应已实现（引入即双计）。
- **「到店/到访」信号（2026-09-29 评估，用户裁决「做静默采集」）**：**四问 #1 其实通过**
  —— 到访 ≠ 浏览的子集（可在店里打开小程序却不看该店详情；也可在家看该店详情），
  两者部分重叠、互不包含。**易错点：别把「采集渠道双计」当成「指标共线」**（上一轮即误判于此）。
  所谓"双计"只有计时器 `VENUE_AUTO_MATCH_RADIUS_M = 50`（44 号 §13.2）一处，**且 2026-10-06 核查
  确认实际无风险**：计时器不写 presence ping（`dance-timer.ts` 用自有 50m 判定，与 presence 完全独立），
  09-29 设计的"单一事实源重构"**未实施** ⇒ 当前不构成双计（登记为遗留项，不是已解决项）。
  #3 曝光闭环**弱**（曝光→到店是多步链路），**但引入新偏差：地理可达性**
  —— 到访人数 ≈ 该店周边活跃用户数，用作跨城排序 = 把"人口密度"当"门店质量"。
  ~~⇒ 必须同城归一化（该店到访 / 该城到访）~~ **⚠️ 2026-10-06 实测推翻此条**：
  该式分母 = 同城**到访**总数，恰是最稀疏的量 ⇒ 小城市被放大（咸阳全市 30 天仅 3 个浏览用户、
  却有 2 个人到访，1 人即 = 25%~50% 份额）**比裸人数噪声更大**。
  正确的分母只能是需求侧基数（浏览人数）⇒ 那就退化成「转化率」，见 2026-10-06 结论。
  **最根本的冲突（选型前必看）**：抗刷要求"无到访背书 → 降权"，发现新店要求
  "无到访（还没人去）→ 不降权" —— **在"到访"这一维度上不可调和**
  ⇒ **到访不适合当"分数修正器"（折减/门槛）**，只适合**加性输入（+同城归一化）**或**独立维度/榜单**。
  逐用户折减（`COUNT(DISTINCT CASE WHEN EXISTS(相关子查询))`）另受 **JPQL 硬约束不可行**
  （须 native/CTE 重写全部列表主查询）。**加性输入可行**：`HEAT_BEHAVIOR` 现有 5 项全是
  标量子查询（`(SELECT COUNT(DISTINCT f.userId) FROM Favorite f WHERE f.venueId = v.id ...)`），
  新项同构即可；注意 `HEAT_BEHAVIOR` 在 `HEAT_SCORE` 出现两次 ⇒ 子查询执行两遍。
  **采集成本 ≈ 0**：首页 `onLoad` 本就定位（`index.ts` L911），`onShow` L1058
  `getUserLocation().then()` 后坐标已保鲜 ⇒ 判定搭便车消费，**零新增 GPS 调用**（禁主动触发定位）。
  **护栏**：判定复用「50m 恰好一家」，0 家/≥2 家/失败一律不记（取严）⇒
  密集区门店（实测 **7.3% = 93 家**）系统性拿不到到访记录，这是取严的必然代价。
  **命名红线**：项目内「打卡」已被占用两次（`/points/check-in` 每日打开打卡 +
  `qwt_venue_activity_checkins` 活动打卡，后者现网 0 行）⇒ 禁再用「打卡/checkin」命名，用「到访」。
  **判定半径实测**（1269 家有坐标门店的邻居分布，可复用于任何邻近判定）：
  50m 7.3% / 100m 10.6% / 200m 15.1% / 300m 20.3% / 1000m 42.2% —— 半径放大不是"覆盖更全"
  而是"错得更多"（室内 GPS 漂移 50~150m 与店间距同量级）。
  **落地路径**：先 **P0 暗跑**（1~2 周只记录不消费）拿真实量级，再决定进不进公式 ——
  止损线：<100 条/周、有到访门店 <30 家/周、或**与 UV 重叠 ≥90%**（说明只是 UV 的影子）即停。
  完整论证见工作区 `quwuting-venue-visit-feasibility-2026-09-29.md` 与
  `quwuting-venue-visit-design-2026-09-29.md`。

### 「到店足迹进排名」定稿结论（2026-10-06，P0 暗跑数据裁决；完整分析见工作区
`quwuting-venue-visit-ranking-analysis-2026-10-06.md`）

**采集实现与 09-29 设计稿不同**（对口径有影响，先记住）：表 = **`qwt_venue_presence_pings`**
（15 分钟桶幂等，非 `qwt_venue_visits`）；端侧只上报 500m 内最近一家的 `distance_m`/`accuracy_m`
（**服务端不复算**，隐私红线）；口径全在查询侧 = `HIT_RADIUS_M = 150`（原 20，10-03 根因修复）+
`CO_LOCATED_RADIUS_M = 50` 同址组 + 营业状态四态归因（NONE/SHARED/ABSORBED/YIELDED）+
**同意门禁**（10-03 起只收"最新一条 consent 显式允许"用户的 ping）。**无 `source` 列**。

**P0 真值（10-01~10-05，生产只读）**：51 条 / 15 人 / 14 店；命中（≤150m）42 条、10 店。
- 止损线 **1/3 通过**：周折 71 条（排除内部账号仅 35）＜100 ✗；命中门店 14 家/周 ＜50 ✗；
  **与 UV 重叠 53% ✓**（归因后 15 组「店-人」中 8 组也浏览过该店；寻梦缘/魅莎/天宝 0% 重叠）
  ⇒ **四问 #1 实证通过**，"到访只是 UV 的影子"被否。
- **账号结构 = 约翰事件同构**：`user 2`（ADMIN）一人 **26 条 = 51%**；排除 admin 后仍有
  `test`/`1` 两个测试号 ⇒ **到访项上线前 `heat.excluded.user.ids` 必须非空**（当前为空）。
- **单店集中度**：一壶淡泊（SUSPENDED）31 条 = 61%（停业店坐标恰为最近邻，路过全记它）。

**核心结论：不能裸加，必须带「免计基数」。**
- 实测 λ≈1：归因后 8 家到访店中 **5 家只有 1 人**（这就是 09-07「89 家收藏恰好 1 人」同类噪声）。
- 裸加（`人数×8`）实测三条错误：**西安「舞美时光」16 名→第 3**（仅 1 人到访）、
  **西安「钜之淋」(CEASED) 57→21（W=15 时→第 5）**、**咸阳整城重排**（全市 30 天仅 3 个浏览用户、
  门店热度全为 1，+8 即翻天）⇒ **破坏力集中在"热度本身没有区分度"的城市**，
  固定权重的裸人数项 = **在热度越弱的地方给越多分**。**别再走"把权重调小"的路**（同 08-27/09-07/09-19）。
- **推荐口径（定稿）**：`到访贡献 = W_VISIT × max(0, 到访人数30d − 2)`，`W_VISIT = 10`。
  免计基数 2 的依据：`P(Poisson(1) ≥ 3) = 8%` ⇒ 门槛 3 把"恰好一个人路过"挡在门外；
  `max(0, n−2)` 从门槛起**连续线性**（第 3 人 = 10 分），避免 n=2→3 的**悬崖**
  （同 09-07 `SORT_WEIGHT_GUARD_MIN_BEHAVIOR` 教训）。W=10 只略高于收藏 8——它是"免计基数
  之上的**边际票**"，信息量低于首票，**禁用 15 以上**。
- **该口径今天 = 零位移**：过门槛的只有南通 3 家（丽莎 4 人 / 抖舞 3 / 寻梦缘 3），且南通
  现次序 1-2-3 不变；全网其他城市无一家过门槛。⇒ 口径落定、影响延后，**不是"加了没影响"的敷衍**。
- **仍不做折减/门槛式降权**（抗刷 vs 发现新店不可调和）；**仍不做同城份额归一**（见上）。

**工程硬约束（比"四套镜像"多一个东西）**：到访人数是派生量（同址组 × 营业状态 × 用户并集），
**JPQL 无派生表能力 ⇒ 必须先落物化汇总表**（如 `qwt_venue_visit_metrics(venue_id, visit_users_30d,
visit_users_7d, group_size, refreshed_at)`，定时任务复用 `VenuePresenceService` 归因），
公式只做标量子查询读它。**绕过归因直接写距离标量子查询 = 违规**（丢掉共享/让渡口径、
同楼竞品各吃一份整楼人流，52 号 §1.1 第 1 条明文禁止）。代价：**到访项有刷新延迟，排序不再全实时**。
**口径分叉必须显式登记**：admin 展示 = 共享口径，排序 = **分摊口径**（同址组都在营时按 1/k 分摊）。

**三个伴随问题（不同时解决，加了也会错）**：
1. 内部/测试账号（见上）——到访是**低基数**信号，内部账号占比远高于它在收藏/反馈里的占比。
2. **停业店与到访证据冲突**：`attribute()` 在"无同址邻居"时返回 NONE、**不看自己状态** ⇒
   停业店只要没有 50m 内邻居就保留证据（实测钜之淋 CEASED 保留 1 人）。
   建议：**公式输入按"不在营记 0"**（排序不容停业店上浮），**admin 保留证据当状态复核线索**
   （"停业但近 30 天有 N 人到访"⇒ 建议复核，48 号域价值）。
3. **同意门禁的基数天花板（结构性，不随时间消失）**：显式允许仅 **11 人**（全网 1045 注册用户）
   ⇒ 到访记录 = 允许用户 × 到店频次，本质是 **1% 自选择子样本**。
   ⇒ **到访永远只能是"稀疏触发的低权项"，不能当主力**；"用实到店人数重排榜单"的期待不成立，
   这不是技术问题而是授权决定的上限。

#### 落地实录（2026-10-06 V38，已实施；下次改到访项先读这段）

**代码落点**：`VenueHeatWeights.VISIT`(=10) / `VISIT_FREE_TIER`(=2) · V38 迁移建
`qwt_venue_visit_metrics` · `VenueVisitMetricsScheduler`（`@Scheduled` 30 分钟；**先整表
`resetAll` 清零再逐店 `upsert`** ⇒ 窗口外自然淘汰，无需记录"上轮有哪些店"）·
`VenuePresenceService.visitSharesForRanking`（分摊份额的唯一产出方）·
`VenueVisitBadgeService`（C 端「到店足迹行」文案）· 四套镜像 + `countHeatCounters` +
`HeatCounters.getVisitusers30d`。

**C 端展示形态：2026-10-06 二轮由"标签行里的胶囊"升级为"独占一行 · 整行可点 → 设置页"**
（用户裁决：胶囊只能陈述事实，用户看完仍不知道「到店足迹」是什么、更不知道怎么参与）。
踩点清单（同族改造照此走，别重新踩）：
- **`catch:tap` 必须挂行容器本身**（`.card-visit-row`，宽度恒 = 整行），禁挂 `<text>` 子节点
  —— 命中区会退化成"文字盒宽的副产物"、随文案长度静默漂移（2026-09-24 reaction 行同款事故）。
- **导航型命中区不设按压态**（同 2026-10-01 卡片根裁决）：反馈 = 目标页出现，触摸态只会闪。
- **组件内直连 `wx.navigateTo` 优于新增事件通道**：目标页固定、不依赖宿主状态时，
  走事件要在 index（双 Tab）+ 收藏列表**三处宿主**各绑一次，多出"某处漏绑 = 某列表点不动"
  的静默缺陷面；先例 = `gift-givers` / `reaction-picker` / `announcement-demo`。
- **门禁已扩到 H9–H11**（`check:venue-card`）：① catch 在容器上 ② 容器无 hover-class
  ③ 子节点零 catch.tap。**三条都做过变异测试**（catch 移到子节点 → H9+H11 红；加 hover-class → H10 红）。

**文案定稿「感谢 N 位舞友自愿分享到店足迹」，三个词各担一责（改前先读
`VenueVisitBadgeService` javadoc）**：「自愿」= 口径+合规（只覆盖"用户显式开启"的子集，
不写会被读成"这家店只有 N 个客人"）／「感谢」= 对贡献的正反馈，也是引导开启的正当性来源
（**感谢是回报，不是诱导** —— 这一句是合规裁决，别删）／「分享到店足迹」= 与设置页开关名
逐字对齐（本行可点过去就是那个开关，用词不一致用户到了设置页会认不出）。
⛔ 一轮稿「已记录 N 位舞友到店」已被否（只陈述事实、不解释来源、也不感谢）。

**五个实现细节（都踩过或差点踩）**：
1. **到访人数可能是小数**（分摊 1/k）⇒ 物化表列用 `decimal(8,2)`，`HeatCounters` 投影声明
   `java.math.BigDecimal`（不要赌 JDBC 自动转 Double）；`VenueHeatService` 的公式文案契约是
   **「N×W」形态且必须乘得起来** ⇒ 加了 `formatVisitCount`（整数显示整数、小数留一位，
   否则 1.5 四舍五入成 "2×10" 会显示 20 而实际 15 —— 文案与数值互相矛盾）。
2. **Java 文本块会剥掉每行尾随空白** ⇒ 源码里的 `) * """ + VISIT` 在最终 SQL 里是 `) *10`（无空格）。
   对拼接产物做文本断言**必须先归一空白**（`replaceAll("\\s+","")`），否则按 `"* 10"` 断言**恒红**
   ——本轮的 `VenueHeatVisitSourceTest` 第一版正是这么写错的，是例行变异测试把它抓出来的
   （**红的是断言不是实现**：这次教训值得记住——"新断言先证明它会红"能同时抓出恒绿与恒红两类废断言）。
3. **`GREATEST` 在 HQL 里可用**（已用 jshell 离线探针实测 `PARSE-OK`）；native MySQL 侧同理
   （实测 `GREATEST(0, COALESCE(...,0) - 2) * 10` 对 NULL 给 0、对 4.00 给 20.00，返回 DECIMAL）。
   ⚠️ 物化表**未落库前**无法跑 native SQL —— 用「等价内联派生表」替换表名做只读验证即可
   （`(SELECT NULL AS venue_id, 0 AS visit_users_30d, 0 AS deleted) m`）。
4. **给 record 加末位字段 = 逐个短重载调用点补 `null` 占位**（本轮实际踩到）：`VenueResponse`
   追加第 31 个组件后，`FavoriteService` 的 **9 参调用 + 1 个新参恰好命中十参重载** ⇒ 新参落到
   `matchedHint` 槽位，编译报 `String cannot be converted to VenueMatchHint`（好的一面：类型不同
   所以编译期就爆了；**若相邻两个字段同类型，它会静默串位**）。连带 `FavoriteServiceTest`
   的 Mockito 桩与 `verify` 也要同步参数个数（strict stubs 参数不符报 `PotentialStubbingProblem`）。
   ⇒ 改 record 后**先 grep 全部重载调用点**，再跑该 record 的所有消费方单测。
5. **收藏列表必须同口径注入**（同 isHot / crowdBadgeText 的历史缺陷模式）：`VenueService` 与

## 二、落地改动清单（四套镜像必须同步）

调整公式项时，权重常量唯一事实源 = `config/VenueHeatWeights`，但**公式本体有四套镜像**：

1. `VenueHeatWeights` — 权重常量与论证注释
2. `VenueRepository.HEAT_BEHAVIOR` — **JPQL/HQL**（列表排序），列用**实体名 + Java 属性名**，枚举用全限定字面量，时间减法带 `day` 单位后缀
3. `VenueRepository.findHotVenueIds` — **native MySQL**（热门判定），用表名，日期用 `DATE_SUB(CURRENT_DATE, INTERVAL n DAY)`
4. `VenueHeatService.computeHeat` — Java 实现 + `formulaText`/`formulaDetail` 文案（前端禁硬编码权重）
   另：`countHeatCounters`（native MySQL）是这些计数器的**取数源**，加新输入项要同步加子查询

**JPQL 硬约束**：无 FROM 派生表能力 → "按用户分组后计数"（如跨天复访）**无法进排序**，进排序须把全部列表主查询 native 化重写（收益/风险比不成立，见 `HEAT_SCORE` 2026-09-02 双算评估结论）。此类指标只能做**展示字段**（`viewCount30d`/`favoriteCount`/`postCount` 既有范式：下发仅供展示、不计入公式）。

**零迁移优先**：新指标优先用已有列/表表达（复访用 `qwt_venue_views(user_id, view_date)`、取消收藏用 V19 `unfavorited_at`、现场人气复用 `GET /venues/{id}/crowd-reports/summary`）——零迁移 = 零 Flyway 风险。确需迁移时走 **`db/migration-mysql`**（先 `ls` 查最大编号；PG `db/migration` 是遗留轨道勿复用）。
