# 生产只读数据取证：把「用户报障」变成可验证命题

## 〇、先划边界（红线，先读再动手）

- **只读**。只允许 `SELECT` / `SHOW`。禁 `INSERT/UPDATE/DELETE/DDL`，禁 `flyway`，禁启动服务。
- 本地 `application-mysql.yaml` 的 datasource **就是生产 RDS**（见该文件顶部注释）⇒ 任何写都会进生产。
- 只用于**取决策依据**，不用于验证代码改动效果。代码改动的本地验证仍止步静态（编译/tsc/门禁）。

## 一、连接入口（唯一可信姿势）

```bash
/opt/homebrew/opt/mysql@8.0/bin/mysql \
  -h rm-bp1xe6rsjf57713004o.mysql.rds.aliyuncs.com -P 3306 \
  -u qwt_app -p'quwuting@2026' qwt_mysql --connect-timeout=8 -e "SELECT ...;"
```

- 凭据源：`quwuting-service/src/main/resources/application-mysql.yaml`（只读用途）。输出会带一条
  password 警告，`2>&1 | grep -v Warning` 去掉。
- 主机名很长，**手打必错**——从 yaml 复制。曾因少一位字符报 `Unknown MySQL server host`。

## 二、真值表（踩过弯路的，先看再写 SQL）

| 事实 | 真值 | 弯路 |
|---|---|---|
| 门店主表 | `qwt_venues`（**有 `qwt_` 前缀**） | 写 `venues` → `Table doesn't exist` |
| **门店状态枚举** | `OPEN` / `SUSPENDED` / `CEASED` / `CLOSED` | ⛔ **`PUBLISHED` 不是门店状态**（那是 `qwt_venue_activities.status`）。写 `status='PUBLISHED'` 恒返回 0 行，会被误读成"没有数据/城市未覆盖" |
| 门店可见性 | 列表只过滤 `deleted = false`，**状态不过滤**（停业/暂停照常展示） | 别自行加状态条件，会算出偏小的覆盖数 |
| `city` 字段形态 | 带「市」后缀（`长沙市`、`上海市`）；1301/1302 如此 | 搜「合肥市」命不中不是因为多了「市」字 |
| 行为事实表 | 目录 = `user/repository/UserBehaviorEvent.java`（**唯一事实源**） | 想找"有没有埋点"别猜，直接读这个枚举 |
| 意见反馈 | `qwt_app_feedbacks`（通用）/ `qwt_venue_feedbacks`（门店纠错） | 两者语义不同，别混 |

## 三、流程（六步，别跳）

1. **把报障改写成可验证命题**。
   例：「用户搜『合肥市』无结果」→ 拆成两问：
   ① 合肥有没有门店？（数据事实）② 关键词匹配逻辑会不会漏掉城市名？（代码事实）
   **两个问题分别取证，禁合并成一句「搜索有问题」。**
2. **模拟后端谓词**。从 `VenueRepository` 复制真谓词到 SQL 跑：
   - 关键词集：`KW_MATCH`（八载体：name/address/description/city/district/tags/两个别名表）
   - 列表过滤：`LIST_FILTERS`；半径：`RADIUS_PREDICATE`（注意 `:city IS NOT NULL` 时恒真）
   - 用**要问的那个词**跑一遍，看命中 0 是"谓词不覆盖"还是"库里真没有"。
3. **区分「匹配失败」与「覆盖缺口」**（本轮最值钱的判据）。
   - 匹配失败 = 换个等价词能命中（如「杭州」↔「杭州市」都能命中 ⇒ 形态无关）
   - 覆盖缺口 = 任何写法都 0 命中，且同城没有别的地方漏（`city` 精确 + `address LIKE` + `name LIKE` 全 0）
   ⇒ **覆盖缺口不是 bug，别去改匹配逻辑**。改错了会把"数据缺口"伪装成"搜索不好用"。
4. **验证产品假设：注释声称的出口/漏斗，真的在收数据吗**。
   文档常写「该空态出口承担 X 的回收」——**这是一条假设，不是事实**。直接查：
   ```sql
   SELECT COUNT(*) FROM qwt_app_feedbacks WHERE content LIKE '%收录门店%';
   ```
   2026-09-30 实测：全表 10 条、**该 prefill 0 条** ⇒ 「缺店线索漏斗由空态出口承担」被数据推翻。
   **通用判据：凡"某出口负责回收某类信号"的注释，必须配一条"它真的收到了吗"的量化检查。**
5. **查行为目录有没有落点**。
   若 `UserBehaviorEvent` 里没有对应事件，说明该行为**结构化不可见**——这解释了"为什么只能靠人肉看日志"，
   也意味着产品处于结构性盲区。此时优先提"补一个最小落点"，而不是只改文案。
6. **结论分三层输出**（禁只给一个"根因"）：
   - **数据层**：库里的事实（覆盖/分布）
   - **语义层**：系统把 A 意图解读成了 B 意图（真缺陷）
   - **承接层**：因为解读错，出口/文案/CTA 也跟着错（用户可见的困惑）

## 四、通用判据（可迁移）

- **自由文本入口必须做语义分诊**：搜索框是全站唯一接受自由文本的地方，用户会用它表达一切
  未覆盖意图（城市名/品类词/拼音）。失败语义 ≠ 只有「没找到这家店」一种。
- **出口必须与意图匹配**：城市需求 ≠ 门店需求。把城市名写进「缺店线索」表单，运营侧收到的是
  不可用线索（读作"一家叫『合肥市』的店"），用户侧白干一次。
- **同一事实禁两套文案**：查空态时必须横向比对**所有**能到达同一空结果的分支
  （`pages/index/index.wxml` 的空态 `wx:if/wx:elif` 链），更常用的入口不能拿到更差的文案。
- **别把日志读成用户行为**：列表搜索有 `SEARCH_DEBOUNCE_MS = 350` 防抖 + 输入即搜
  ⇒ 打「合肥市」会产生最多 3 次请求（合 / 合肥 / 合肥市）。日志里"多次"≠ 用户重试多次；
  要坐实重试，判据 = **同一会话内同一关键词最终态出现 ≥2 次**或间隔数秒的重复。

## 五、体感类报障（「慢」/「闪」）的取证顺序

> 2026-10-03 立（判例：用户报障「我的页底部小程序码每次加载都很慢、页面闪一下，是不是每次都动态生成」）。
> 这类报障最容易犯的错是**直接接受用户给的因果假设**（"它每次重新生成吧"）就动手优化。
> 顺序固定，前三步专门用来**证伪服务端**——证伪不掉才有资格谈优化。

1. **先找该资源的「物化/缓存载体」，用时间戳证伪"每次重做"**。
   - 资产表：`SELECT asset_key, byte_size, created_at FROM <表> ORDER BY created_at DESC`。
     `created_at` 距今天数 = 期间**没有**重新生成过。
   - 再对线上连发 3–5 次请求比 **字节 MD5**（`md5 /tmp/x{1,2,3}.jpg`）：全等 ⇒ 同一份字节。
   - 两者合一即可下结论"不是动态生成"，**不需要**去读微信后台或加日志。
2. **耗时拆解必须带基线**：同主机连发图片接口 + 一条**轻量 JSON 接口**（如 `/venues/cities`），
   差值才是这条路径的服务端成本。判例实测：图片 TTFB 100ms − JSON 基线 82ms ⇒ 服务端只占
   **~15–20ms**。⛔ 只报总耗时会把自己公网 RTT（本次 82ms）读成"服务端慢"。
   ⚠️ 本机 curl 若走代理会出现 `HTTP/1.1 200 Connection Established` 行，RTT 偏高但**基线对照仍有效**。
3. **载荷体积单列一项，与「显示槽位」比**：`Content-Length` vs 实际渲染尺寸。
   判例：430×430 / **91099 B** 的码图显示在 260rpx（2x=260px、3x=390px）槽位 ⇒ **约 2–3 倍超配**
   （根因常是图心有一张彩色插画/渐变，JPEG 压不动）。这是"慢"的第二大来源，且能直接量化。
4. **客户端三个固定疑点，逐个在代码里查，不问用户**：
   - `lazy-load`：请求只在滚进可见范围才发 ⇒ **零预加载**，等待必然发生在用户正看着它的那一刻；
   - **占位底色**：容器/磁贴有没有硬编码底色（`#ffffff`）。有 ⇒ 终态到达前它先画一个**空白块**，
     观感就是"闪一下"。判据 = **占位必须与终态同形不同色**（同尺寸同位置，只换材质）；
   - 客户端缓存是否真命中：微信 image 对网络图**不完全按我们的 Cache-Control 走**
     （官方社区置顶帖：客户端强缓存、换图后连删小程序都不更新）。
5. **结论必须带一个「30 秒可自证」的判定实验**，把本地复现不了的那一步交给用户一次分辨
   （例：开发者工具 Network 面板看该图是 `(disk cache)` 还是每次 200 + 全量字节）。
   ⛔ 禁止把不确定性包装成结论，也禁止为了"闭环"去跑真机/连库冒烟（本地验证止步静态）。
6. **同一形态可能挂两条生命周期不同的通道，先确认用户看的是哪一条**：
   判例 = 平台码（DB 内容指纹物化，永不重生成）vs 门店码（进程内 24h 缓存，
   **进程重启后第一次必外呼微信**）。"都慢"的报障里，两条的修法完全不同。

## 六、「归属 / 数字搬家」类报障（2026-10-08 判例，到访与一切"派生归属"的展示）

> 判例：用户报「丽莎歌舞厅列表页的『感谢 6 位舞友 · 10 次到过这附近的足迹』**算到一壶淡泊音乐酒吧头上了**」。
> 类特征：**同一批数字从一家店"移动"到另一家店**（或本店该有却没有）。这类报障的输入面很窄，
> 固定按下面顺序取证，一次到位（判例全程 ≈ 半小时）：

1. **先找「触发动作」= 近期被改动的输入**。归属类展示的输入只有三样：门店坐标 / 门店状态 / 落点数据。
   一条 SQL 扫**近 48h 被改的门店**：`SELECT id,name,status,updated_at FROM qwt_venues WHERE updated_at >= … `
   （判例：当日唯一变更 = 121 丽莎坐标 00:48 被维护 ⇒ 与 120 从"坐标重合"变为 95m，这就是全部答案的一半）。
2. **量几何，对照三个阈值**：对涉事门店跑 `ST_Distance_Sphere` 全对距离 ——
   50m（同址归因）/ 150m（C 侧展示半径，2026-10-08 起）/ 150m（命中容差）。
   判例 95m：> 50 ⇒ 旧实现「同址组破裂 ⇒ 归属搬家」；≤ 150 ⇒ 新口径「两店都应显示附近」一眼可判。
3. **查落点**：`qwt_venue_presence_pings` 按 `venue_id` 聚合（判例：32 条全在 120 ⇒ 谁持有证据、
   谁只是被端侧「最近一家」扫到）。
4. **对照物化表**：`qwt_venue_visit_metrics`。⚠️ **被清零但本轮未重算的残留行**会保留上次的
   `group_size` / `share_in_operation` 旧值（`resetAll` 只清三列业务值）——别把残留读成"现算结果"。
5. **新旧口径 SQL 模拟对照**（各写一条只读 SQL 重算，判定"数字本身对不对"）：
   判例新口径 = 6 人 / 10 次（对）——**数字对、归属错** ⇒ 结论落「展示模型」而非「取数」。
6. **结论必须三分**：**数字错（取数/口径 bug）** vs **归属错（展示模型 bug）** vs **触发是数据维护（流程）**
   ——三者修法完全不同；禁把"触碰动作"当根因（判例：坐标维护只是触发器，根因是展示层做了
   不可判定的门店级归属）。
